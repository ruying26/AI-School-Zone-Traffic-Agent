# Coursework demo walkthrough

## Suggested sequence

1. Open the project in VS Code and show `config.json` (min green 15 s, yellow 3 s,
   all-red 2 s, pedestrian urgency target 30 s).
2. Explain `fuzzy_logic.py`: the 3x3 age versus disagreement rule table.
   A high-confidence but ageing reading can require re-observation.
3. Show `q_learning.py` and `artifacts/q_table.json`, generated by 1,500 training episodes.
4. Run `python -m unittest discover -s tests -v` and show the test count.
5. **Recommended:** Run `python visualize.py --scenario all --open`. This opens a
   browser dashboard showing the four-way junction with changing lights, queue cars,
   the AI decision trace, sensor reliability, warnings, and the queue-history graph.
   Choose `uncertainty` to show camera re-observation and fallback, or `failures` to
   show manual override and API faults. Use Play, Pause, Next and the time slider.
   If preferred, run `python main.py --scenario uncertainty --verbose --every 5`
   in a terminal to confirm the dashboard values come from Python log entries.
6. Run `python evaluate.py` and open `artifacts/summary.json` or `artifacts/evaluation.csv`.
   The model is frozen during evaluation.

## What to point out in the terminal

- `Q-learning permitted`: a fresh and sufficiently consistent camera observation.
- `Re-observe camera`: the fuzzy score is medium, e.g. when a frame is ageing.
- `Safe fallback`: missing, unreliable, or contradictory sensor readings.
- `proposed_action` and `allowed_actions`: the trained AI can choose **only** safe actions.
- `Manual override`: a person requests an action, still constrained by the local controller.
- `timeout` / `Blocked: unconfirmed signal state`: API readback and no-blind-retry handling.
- `pedestrian_wait_over_target_seconds`: evidence when the 30 s urgency target was missed.

```bash
python visualize.py --scenario all --open
```

## Questions a lecturer might ask

**Where is the AI?** In `q_learning.py` and `controller.py`. The Q-table is trained from
simulated rewards and determines actions when observations are trusted.

**Why fuzzy logic?** A single camera confidence score can overlook stale or
inconsistent frames. The fuzzy rules combine confidence with frame age and
recent-reading disagreement to decide whether to use Q-learning, re-observe, or fall back.

**What happens when the camera fails?** The agent does not treat missing queue
counts as zero. It uses the safety-constrained local fallback controller.

**Why can pedestrians wait more than 30 seconds?** Thirty seconds is an urgency
trigger, not an absolute service deadline. An existing WALK, pedestrian
clearance, and the next minimum vehicle green can make immediate service unsafe.
The metric exposes those misses rather than hiding them.

**What are the limitations?** Simulated demand and confidence, one camera stream,
small discretised Q-table, and a simplified traffic controller. This is a
coursework experiment, not a device ready for a public road.

## What to point at in the browser

1. Traffic lights: the active signal is green, the opposing direction is red. Yellow
   and pedestrian clearance are separate stages in the simulator.
2. Queue counts and chart: these are the `state_after` values stored by `main.py`,
   not imaginary traffic estimates. The car icons are illustrative.
3. Agent decision monitor: `Q-learning permitted` and Q-values show policy usage.
   The allowed-action list shows how the safety controller can restrict the AI.
4. Camera uncertainty: lower fuzzy reliability can cause re-observation or fallback.
5. Manual/API failures: point to the recorded command status, alert and reason.
6. Evaluation: the grouped bars come from the **separate ten-seed** evaluation;
   don't describe them as results of the current single replay.

The visualization does not physically control traffic lights. All scenarios are synthetic.
